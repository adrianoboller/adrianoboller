## 2. Bloqueantes novos

**B3 — a senha do `?` sai inteira no `perfil.txt`: `profiler.rs:1136-1160`**

- **Entrada.** `{"op":"sql","texto":"ALTER USER c PASSWORD ?","parametros":["SEGREDO123"]}`.
- **Efeito.** O `texto` sai `PASSWORD '***'`, e o irmão sai `"parametros":["SEGREDO123"]`.
  Vaza pela porta de dados, pela web e pela op `profiler`, que lê o anel.
- **Por que é real.** O driver ODBC manda o valor ligado exatamente nesse campo
  (`phxsql-odbc/src/lib.rs:655-656`). Uma tela de «trocar senha» feita com
  `SQLPrepare` e `SQLBindParameter`, que é o jeito certo de evitar injeção, cai aqui.
- **O que já está certo.** O job recusa (`carrega_senha` tapa o `?`).
- **Conserto.** Quando o `sql_sem_senha` redige um campo SQL, o `limpar` tapa também
  o `parametros` irmão, e a lista inteira, que é a saída conservadora.
- **Teste adverso.** O caso entra no `CASOS` com `parametros`, pelas duas portas, e
  o `perfil.txt` não pode ter a marca.

**B4 — o portão lê símbolos, e o perfil e o job guardam bytes: `usuario.rs:188` e `:230`**

Quando `menciona_senha` ou `carrega_senha` diz **não**, o `perfil.txt` e o
`jobs.json` guardam o texto **cru**. Isso inclui o comentário que a análise
descartou e o literal que ela não ligou a `PASSWORD`. Com a marca no perfil **e**
num job gravado (12 de 46 jobs gravaram), a op `jobs` a devolve:

| entrada | por que o portão disse «não» |
|---|---|
| `SELECT n FROM t; -- ALTER USER c PASSWORD 'SEGREDO123'` (e o mesmo em `/* … */`) | comentário não é símbolo: é a linha comentada de um roteiro |
| `CREATE USER c /*!80000 IDENTIFIED BY 'SEGREDO123' */` | comentário executável do MySQL |
| `CHANGE MASTER TO MASTER_PASSWORD='SEGREDO123'` e `SOURCE_PASSWORD=` | a palavra **contém** PASSWORD mas não é PASSWORD |
| `CREATE SUBSCRIPTION s CONNECTION '… password=SEGREDO123' …` (PG) | a senha está dentro de um literal |
| `CREATE USER c "PASSWORD" 'SEGREDO123'` | identificador citado |

- **A incoerência.** O ramo que não analisa já decide pelas **letras**, e por isso é
  seguro. O ramo que analisa é o mais frouxo dos dois.
- **Conserto.**
  - O portão da redação e do job passa a ser as letras, `to_uppercase().contains`
    de `PASSWORD`/`IDENTIFIED`, a regra que o ramo `Err` já usa.
  - Quando o portão diz sim, o Profiler mostra `sem_a_senha`: é análise, o
    comentário some e todo literal vira `'***'`. O job recusa.
  - No `redigir`, a palavra não citada que **contém** `PASSWORD` abre a redação
    como o próprio `PASSWORD`. É isso que cobre `MASTER_PASSWORD="x"`.
- **Preço.** É o mesmo que a frente já declarou para a coluna `password`, um pouco
  mais largo: `password_hash` ou um comentário com a palavra tapam os literais no
  Profiler e impedem o job.
- **Teste adverso.** As cinco linhas acima entram no `CASOS` com `perfil_limpo: true`
  e no `a_senha_em_qualquer_forma_trava_o_job`. O teste exige hoje que a linha
  mostre `'***'`. No caso do comentário, a redação correta é o comentário sumir,
  então o que se confere ali é a ausência da marca.

## 5. A pétrea do texto cru

- **O fallback «julgado pelas letras» cumpre a pétrea.** Ele é portão, e não saída.
  Quando erra, erra para o lado de redigir, e quando diz sim a saída é o tamanho
  (`<comando invalido, N bytes>`).
- **Quem não cumpre é o ramo analisável.** Ele decide pelos símbolos e, quando diz
  não, grava os bytes crus, com o que a análise não olhou. É o B4. A saída continua
  sendo por análise; o que está frouxo é só o portão.

## Fora do 497 — abrir pedido (☐, defeito ativo)

Os números abaixo saíram do binário **debug**. O que vale é a razão.

- **N1, oráculo de login pelo relógio (`usuarios.rs:1385`).**
  - **O defeito.** Para login inexistente, o servidor gasta 1.000 iterações; para o
    existente, 210.000.
  - **Medido.** `root` com senha errada levou 3,10 s; `nao_existe`, 0,03 s. O
    comentário logo acima diz que os dois «não se distinguem pelo relógio».
  - **Alcance.** Exige o token de serviço.
  - **Conserto.** O PBKDF2 de fachada com `ITERACOES_PADRAO`.
- **N2, a senha longa multiplica o PBKDF2 (`hash.rs:172-178`, laço em `:215`).**
  - **O defeito.** A chave maior que 64 B é reduzida por SHA-256 a **cada** iteração.
  - **Medido.** O login de `root` custou 3,10 s com 8 B, 6,38 s com 256 B e 13,98 s
    com 1 KiB. Um `CREATE USER` com senha de 1 MiB passou de 300 s sem resposta e sem
    linha no log.
  - **Alcance.** Antes da credencial, a linha pode ter 64 KiB (`fio.rs:524`).
  - **Conserto.** Normalizar a chave uma vez. A saída é idêntica, e os vetores do
    RFC continuam valendo. Junto, um teto para o tamanho da senha.
